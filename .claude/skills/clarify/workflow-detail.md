# /clarify ワークフロー詳細

本ファイルはSKILL.mdの補助リソース。各ラウンドの具体的な質問例・弁証法的構造・使用例を収録。

---

## セッション開始: 説明責任フレーミング

セッション冒頭で、以下のフレーミングを必ず行う:

```
AI: 「/clarify を開始します。[テーマ]についての暗黙知を引き出していきます。

     ここで整理する判断は、そのまま /spec の仕様に反映され、
     チームの実装指針になります。
     「なぜその判断をしたか」を後から説明できる形で進めましょう。

     まず、[テーマ]について一番大事にしたいことを、
     自分の言葉で教えてください。」
```

ポイント:

- 「後から説明できる」と伝えることで、主体的思考を喚起
- 選択肢を出さず、ユーザーの言葉を引き出す
- 判断がspec→実装に直結することを意識させる

## Round 1: 定義と基本戦略

**目的**: 曖昧な言葉を具体化し、基本方針を確認

**自由回答ファースト**: 各質問で選択肢を先に提示しない。まずオープンエンドで問い、回答を受けてからアナロジーで確認する。

```
質問カテゴリ:
1. 定義の明確化
   - 「〇〇」とは具体的に何を指す？
   - 「成功」の定義は？

2. シグナルの優先順位
   - 暗黙的な入力をどう解釈する？
   - 明示的 vs 暗黙的の優先度は？

3. コールドスタート
   - データがない状態でどう対応？
   - 初期フェーズの戦略は？
```

## Round 2: トレードオフの掘り下げ

**目的**: 二項対立する選択肢の判断基準を明確化

```
質問カテゴリ:
1. 時間的変化
   - 過去のデータはどう減衰させる？
   - 「復活」のタイミングは？

2. UIトレードオフ
   - 誰が選ぶか？（システム vs ユーザー）
   - ユーザー負担と情報取得のバランスは？

3. 属性の考慮
   - 副次的属性をどう扱う？
   - 重み付けの基準は？
```

## ★ 中間リフレクション（Mid-Session Reflection）

**タイミング**: Round 2 完了後、CTOチェックポイントの前

```
AI: 「Round 1-2で[N]個の判断をしました。
     ここまでの対話を振り返って、2つ聞かせてください:

     1. ここまでの質問の中で、
        『聞かれて初めて意識した』ものはありましたか？
     2. まだ言語化できていないけど、
        頭の中にある『もやもや』はありますか？」
```

ルール:

- **2問のみ**（認知負荷を最小化）
- 形式的でなく、感覚的に答えられる問い
- 「もやもや」が出た場合、Round 3以降の質問に反映する
- 「特にない」の回答も尊重する（深追いしない）

## ◆ 弁証法的CTO チェックポイント

**タイミング**: 中間リフレクション完了後（主要なトレードオフ判断が出揃った時点）

```
AI: 「ここまでの主要な決定を整理します:
     1. [決定事項1]
        前提: [前提レジスターから引用]
     2. [決定事項2]
        前提: [前提レジスターから引用]

     まず前提を揺さぶらせてください。
     もし『[前提1の否定]』だったら、決定1はどう変わりますか？

     次に、反対の立場から考えてみてください。
     もし [決定事項1の反対] だったら、何が良くなりますか？
     逆に何が困りますか？

     前提と反対の立場を検討した上で、
     元の判断を維持しますか？それとも修正したい点がありますか？」
```

ルール:

- **最も影響の大きい1〜2件**に絞る
- 前提レジスターから該当決定の前提を引用し、「この前提が崩れたら？」と問う
- ユーザーが「維持する」と回答した場合、理由を記録する（Decision Provenance: ✅）
- 「前提を検証し、反対の立場を考えた上で維持」は最も強い確信の証拠

## Round 3: 技術的制約

**目的**: 実装上の制約を確認し、現実的な解を導く

```
質問カテゴリ:
1. UIの粒度
   - どこまで細かく設定させる？
   - 複雑性 vs 精度のバランスは？

2. 計算リソース
   - リアルタイム vs バッチの判断基準は？
   - コスト許容範囲は？

3. 段階的アプローチ
   - MVPで割り切ってよい機能は？
   - 後回しにできる要素は？
```

## Round 4: Devil's Advocate（悪魔の代弁者）

**目的**: AIが意図的にこれまでの決定に反論し、決定の堅牢性を最終検証する

```
AI: 「ここまでの判断を踏まえて、あえて反論させてください。
     これは私の意見ではなく、堅牢性を検証するための
     Devil's Advocate（悪魔の代弁者）です。

     ■ [決定事項X] について:
     もし[反論の観点]だとしたら、[具体的リスク]が考えられます。
     この懸念に対して、あなたはどう考えますか？

     ■ [決定事項Y] について:
     [代替アプローチ]を選ばなかった理由は明確ですか？
     後から振り返った時に『なぜこうしたか』を説明できますか？」
```

ルール:

- **必ず「Devil's Advocate である」と宣言**してから反論する
- 反論は**最大2件**に絞る
- 反論の観点: スケーラビリティリスク / ユーザー体験の盲点 / 技術的負債 / 代替アプローチの見落とし
- ユーザーの回答は Decision Provenance に「😈 DA検証済み」として記録

## Round 5: 最終確認と確信度キャリブレーション

**目的**: 残った不明点を解消し、決定事項を確定。各判断の確信度を測定。

```
質問カテゴリ:
1. 動的調整
   - パラメータは固定？動的？
   - 調整の頻度・トリガーは？

2. 新規アイテム対応
   - 新着の扱いは？
   - 既存との統合方法は？

3. MVP範囲の最終確認
   - 後回しにしてよいものの再確認
   - 必須 vs Nice-to-have の線引き

4. 確信度キャリブレーション
   - 各決定事項の確信度を 高/中/低 で確認
   - 「低」の項目は /spec で再検討フラグを付与
```

確信度キャリブレーション実行例:

```
AI: 「最後に、各決定事項の確信度を確認させてください。
     『後から説明できるか』を基準に、高/中/低 で教えてください。

     1. [決定事項1]: あなたの確信度は？
     2. [決定事項2]: あなたの確信度は？
     ...

     確信度「低」の項目は、/spec で詳細検討のフラグを立てます。」
```

## 弁証法的質問三層構造（Dialectical Question Triad）

各ラウンドの3問を、以下の3層で構成することを**推奨構造**（強制ではない）とする。

| 層        | 名称                     | 機能                  | 質問パターン                                               |
| --------- | ------------------------ | --------------------- | ---------------------------------------------------------- |
| **第1層** | テーゼ（主張の引き出し） | 産婆術                | 「〜について、あなたの考えは？」（自由回答ファースト維持） |
| **第2層** | アンチテーゼ（揺さぶり） | 前提探索 / エレンコス | 「なぜそう思う？」「それが成り立たない条件は？」           |
| **第3層** | ジンテーゼ（統合と深化） | 帰結連鎖 / メタ認知   | 「ここまでの話を統合すると、どう定義できる？」             |

適用例:

```
Q1（テーゼ）: 「推薦機能で一番大事にしたいことを、
              自分の言葉で教えてください。」
User: 「ユーザーが好みに合った記事に出会えること」

Q2（アンチテーゼ）: 「『好みに合った』が重要とのことですが、
     なぜ『好み以外の記事に出会う』ことは価値が低いと考えましたか？
     あえて『好み以外の記事を推薦する』方針だとしたら、何が困りますか？」
User: 「発見もあっていいけど、まずは外さない推薦がベース」

Q3（ジンテーゼ）: 「つまり、あなたの言う『好みに合った』は
     『好みを外さないことがベースで、その上に発見がある二層構造』
     という理解で合っていますか？」
User: 「そう、まさにそのイメージ」

決定事項: 推薦の二層構造（好みベース + 発見レイヤー）（出所: 🔄）
前提記録: 「好み以外にも価値があるが、優先度は低い」（📐 前提明示化済み）
```

運用ルール:

- 推奨パターンであり、すべてのラウンドで厳密に3層を踏む必要はない
- **ただし第2層（アンチテーゼ/前提探索）の省略は禁止**
- 第2層の質問は「なぜ？」「それが成り立たない条件は？」「その前提は何？」のいずれか

## 連続的エレンコス（Continuous Elenchus）

決定事項の記録時に、**過去の決定との矛盾を自動検出**するメカニズム。

**トリガー条件**: 回答を決定事項として記録する際、以下を自動チェック:

1. 過去の決定事項と論理的矛盾がないか
2. 過去の前提と新しい決定が整合するか
3. 新しい決定が過去の決定の帰結に影響するか

**矛盾検出時の行動**:

```
AI: 「一点確認させてください。
     Round [N]で『[過去の決定]』と判断しましたが、
     今の『[新しい決定]』は異なる方向性です。
     この2つをどう折り合いをつけますか？」
```

- ラウンドの質問枠とは独立して矛盾指摘を1つ挟む
- ユーザーの解消回答を記録（出所記号: 🔗 整合性検証済み）
- 矛盾がない場合は透過的（何も起きない）

## 導入しないソクラテス的要素

| 要素                   | 不採用の理由                             |
| ---------------------- | ---------------------------------------- |
| アポリア（行き詰まり） | 目的が知的探求ではなく意思決定支援のため |
| ソクラテス的アイロニー | AI文脈で不自然。信頼関係を損なう         |
| 無制限のWhyチェーン    | 第2層で吸収済み。認知疲労リスク          |
| 有機的対話への移行     | 5ラウンド構造で弁証法を実現済み          |

## 質問生成ルール

### 質問の優先順位

1. **ブロッカー質問**: 回答なしでは仕様が書けない
2. **方向性質問**: 複数のアプローチがあり選択が必要
3. **詳細質問**: 細部の仕様を確定する

### アナロジー活用ルール

抽象的な回答に対して、エンジニアリング概念を比喩として返し具体化を促す。

原則:

1. 常にエンジニアリング概念をベースに（ユーザーは全員エンジニア）
2. 二者択一の対立概念を提示し「どちら寄り？」と聞く
3. ユーザーが別ドメインの比喩を使ったら、そちらに乗り換える

難易度Tier:

| Tier   | 対象         | 概念例                                      | 開始条件                     |
| ------ | ------------ | ------------------------------------------- | ---------------------------- |
| Tier 1 | 全エンジニア | 変数vs定数、同期vs非同期                    | 相手が「それ何？」と聞いた時 |
| Tier 2 | 実務経験者   | モノリスvsマイクロサービス、REST vs GraphQL | **初回デフォルト**           |
| Tier 3 | 設計経験者   | CAP定理、CQRS、Saga                         | 相手が上級概念を自ら使った時 |

### 質問のフォーマット

```markdown
## Round X: [フェーズ名]

### 質問 1: [質問タイトル]

[質問本文]

**選択肢（参考）:**

- A: [選択肢Aの説明]
- B: [選択肢Bの説明]
- その他: 自由回答も可

### 質問 2: [質問タイトル]

...
```

## 使用例

### 例1: 推薦ロジックの暗黙知抽出

```
ユーザー: 「推薦機能を作りたいんだけど、要件を整理して」

[自動] /clarify Skill発動

Claude: /clarify を開始します。推薦機能の暗黙知を引き出していきます。
     （説明責任フレーミング）
     まず、推薦機能で一番大事にしたいことを、自分の言葉で教えてください。

ユーザー: 「ユーザーが自分の好みに合った記事に出会えること」

Claude: なるほど、「好みに合った記事への出会い」ですね。
     いくつか掘り下げさせてください。

## Round 1: 定義と基本戦略

### 質問 1: 「好み」の意味
     あなたが言う「好み」とは、具体的にどんな情報を指しますか？

ユーザー: 「ジャンルとか、読んだことある記事の傾向かな」

Claude: 「ジャンル」と「閲覧傾向」の2軸ですね。
     一点気になるのは、明示的なシグナルだけだと
     データ量が少なくなりがちです。
     それでも明示的優先で問題ないですか？

ユーザー: 「暗黙的は補助的に使う感じで」

## ◆ CTO チェックポイント
Claude: あえて反対の立場から。もし「暗黙的シグナルを主軸にする」だったら？

ユーザー: 「データ量は増えるけどノイズも多い。明示的優先で」

Claude: 反対の立場を検討した上で維持、了解です。（出所: ✅）

## Round 4: Devil's Advocate
Claude: 堅牢性検証のため、あえて反論させてください。
     オンボーディング方式は離脱率上昇リスクがあります。

ユーザー: 「ジャンルの多様性が理由。質問は最小限にする」

Claude: DA検証済みとして記録します。（出所: 😈）
```

## 弁証法的質問三層構造ガイド

各ラウンドの3問を、以下の弁証法的三層で構成することを**推奨パターン**とする。

| 層        | 名称                     | 機能                  | 質問パターン                                     |
| --------- | ------------------------ | --------------------- | ------------------------------------------------ |
| **第1層** | テーゼ（主張の引き出し） | 産婆術                | 「〜について、あなたの考えは？」（自由回答）     |
| **第2層** | アンチテーゼ（揺さぶり） | 前提探索 / エレンコス | 「なぜそう思う？」「それが成り立たない条件は？」 |
| **第3層** | ジンテーゼ（統合と深化） | 帰結連鎖 / メタ認知   | 「ここまでの話を統合すると、どう定義できる？」   |

**運用ルール:**

- 全てのラウンドで厳密に3層を踏む必要はない（トピックの性質に合わせて柔軟に調整可能）
- **ただし、第2層（アンチテーゼ/前提探索）の省略は禁止**
- 第1層は既存の「自由回答ファースト」原則をそのまま維持
- 第3層ではアナロジーを「確認」として使用可

**適用例（Round 1: 定義と基本戦略）:**

```
Q1（テーゼ）: 「推薦機能で一番大事にしたいことを、自分の言葉で教えてください。」
User: 「ユーザーが好みに合った記事に出会えること」

Q2（アンチテーゼ）: 「『好みに合った』が重要とのことですが、
     なぜ『好み以外の記事に出会う』ことは価値が低いと考えましたか？
     あえて『好み以外の記事を推薦する』方針だとしたら、何が困りますか？」
User: 「発見もあっていいけど、まずは外さない推薦がベース」

Q3（ジンテーゼ）: 「つまり、あなたの言う『好みに合った』は
     『好みを外さないことがベースで、その上に発見がある二層構造』
     という理解で合っていますか？
     モノリスvsマイクロサービスで言えば、
     堅実なコアの上にオプション機能を載せる感覚？」
User: 「そう、まさにそのイメージ」

決定事項: 推薦の二層構造（好みベース + 発見レイヤー）（出所: 🔄）
前提記録: 「好み以外にも価値があるが、優先度は低い」（📐 前提明示化済み）
```

## 定義の明確化

**目的**: 曖昧な言葉を具体的な定義に落とし込む

### テンプレート

#### 基本形

```markdown
### 質問: 「[用語]」の定義

「[用語]」とは具体的に何を指しますか？

**考慮すべき観点:**

- [観点1]
- [観点2]

**例:**

- [具体例A]: [説明]
- [具体例B]: [説明]

**アナロジー例（抽象回答時に使用）:**

- 「シンプル」→ 「モノリス的な一枚岩？それとも疎結合だけどインターフェースはシンプル？」
- 「柔軟」→ 「設定ファイル的な柔軟さ？プラグイン的な拡張性？API的な汎用性？」
- 「ちゃんと」→ 「型安全の話？バリデーションの話？テストカバレッジの話？」
```

#### 適用例

```markdown
### 質問: 「好み」の定義

「好み」とは具体的に何を指しますか？

**考慮すべき観点:**

- 明示的な意思表示（Like/Dislike）
- 行動から推測される嗜好（閲覧時間、再訪問）
- 過去の選択履歴

**例:**

- 明示的好み: ユーザーがLikeボタンを押した記事
- 暗黙的好み: 3分以上閲覧した記事
```

```markdown
### 質問: 「成功」の定義

この機能における「成功」とは何で判断しますか？

**考慮すべき観点:**

- ユーザー満足度
- ビジネス指標
- 技術的パフォーマンス

**例:**

- ユーザー視点: 欲しい情報がすぐ見つかる
- ビジネス視点: コンバージョン率向上
- 技術視点: レスポンス時間 < 500ms
```

## シグナルの優先順位

**目的**: 複数の入力シグナルの優先度を決定する

### テンプレート

```markdown
### 質問: シグナルの優先順位

以下のシグナルをどのような優先順位で扱いますか？

| シグナル | 例   | 信頼度 |
| -------- | ---- | ------ |
| 明示的   | [例] | 高     |
| 暗黙的   | [例] | 中     |
| 推測     | [例] | 低     |

**選択肢:**

- A: 明示的シグナルのみ使用
- B: 明示的を優先、暗黙的を補助的に使用
- C: 両方を同等に扱う
```

#### 適用例

```markdown
### 質問: ユーザー嗜好シグナルの優先順位

ユーザーの「好み」を判断する際、以下のシグナルをどう優先しますか？

| シグナル | 例                                 | 信頼度 |
| -------- | ---------------------------------- | ------ |
| 明示的   | Like/Dislikeボタン、お気に入り登録 | 高     |
| 暗黙的   | 閲覧時間、スクロール深度           | 中     |
| 推測     | 類似ユーザーの行動                 | 低     |

**選択肢:**

- A: 明示的シグナルのみ使用（精度重視）
- B: 明示的を優先、暗黙的を補助的に使用（バランス）
- C: 両方を同等に扱う（データ量重視）
```

## コールドスタート

**目的**: データ不足時の対応戦略を決定する

### テンプレート

```markdown
### 質問: コールドスタート戦略

[対象]のデータがない状態で、どう対応しますか？

**選択肢:**

- A: [戦略A] - [メリット/デメリット]
- B: [戦略B] - [メリット/デメリット]
- C: [戦略C] - [メリット/デメリット]

**考慮事項:**

- 初期体験の品質
- データ収集の速度
- 実装コスト

**アナロジー例:**

- 「とりあえず動けばいい」→ 「デフォルト値をハードコードして後で差し替える感じ？それともfallback chainを最初から組む？」
- 「安全策で」→ 「Circuit breaker的に、データ不足なら安全な既定値にフォールバック？」
```

#### 適用例

```markdown
### 質問: 新規ユーザーへの初期推薦

新規ユーザー（行動履歴なし）への初期推薦はどうしますか？

**選択肢:**

- A: 人気順で表示 - 安全だが個別化なし
- B: ランダム表示 - 多様性あるがノイズも多い
- C: オンボーディングで好みを聞く - 精度高いが離脱リスク

**考慮事項:**

- 初期体験の品質: どれだけ早く価値を感じてもらえるか
- データ収集の速度: 個別化に必要なデータをどう集めるか
- 実装コスト: オンボーディングUIの開発工数
```

## 成功指標

**目的**: 測定可能なKPIを定義する

### テンプレート

```markdown
### 質問: 成功の測定方法

この機能の「成功」を何で測定しますか？

**指標候補:**
| 指標 | 計算方法 | 目標値 |
|------|----------|--------|
| [指標1] | [計算式] | [目標] |
| [指標2] | [計算式] | [目標] |

**選択肢:**

- A: [主要指標]を最優先
- B: [複数指標]のバランス
- C: 段階的に指標を追加
```

#### 適用例

```markdown
### 質問: 推薦品質の測定方法

「適切な推薦」を何で測定しますか？

**指標候補:**
| 指標 | 計算方法 | 目標値 |
|------|----------|--------|
| CTR | クリック数 / 表示数 | > 5% |
| 滞在時間 | 推薦経由の平均閲覧時間 | > 2分 |
| 再訪率 | 推薦経由で戻ってくる率 | > 30% |

**選択肢:**

- A: CTRを最優先（短期的効果重視）
- B: 滞在時間を重視（エンゲージメント重視）
- C: 複合指標でバランスを取る
```

## 時間的変化

**目的**: データの鮮度や減衰の扱いを決定する

### テンプレート

```markdown
### 質問: 時間経過による[対象]の扱い

[対象]は時間経過でどう変化させますか？

**考慮事項:**

- 減衰: どのくらいで古くなる？
- 復活: 再度有効になる条件は？
- 更新: いつ再計算する？

**選択肢:**

- A: 時間減衰あり（[期間]で半減）
- B: 時間減衰なし（永続）
- C: 明示的なリセットまで有効

**アナロジー例:**

- 「古いのは消したい」→ 「TTL付きキャッシュみたいに自動で期限切れ？それともsoft deleteで論理的に非表示にするだけ？」
- 「状況による」→ 「Eager invalidation（変更があったら即無効化）？それともLazy invalidation（アクセスされた時に鮮度チェック）？」
```

#### 適用例

```markdown
### 質問: Dislikeの時間的扱い

ユーザーがDislikeした記事は、どのくらいの期間表示を抑制しますか？

**考慮事項:**

- 減衰: 永久にDislikeを維持？それとも時間で薄まる？
- 復活: 「もう一度見たい」と思う可能性は？
- 類似: Dislikeした記事に「類似」した記事の扱いは？

**選択肢:**

- A: 永久にDislike維持
- B: 6ヶ月で減衰（再表示される可能性あり）
- C: 明示的に「解除」するまで維持
```

```markdown
| システム | [メリット] | [デメリット] |
| ユーザー | [メリット] | [デメリット] |
```

## 属性の考慮

**目的**: 副次的な属性の扱いを決定する

### テンプレート

```markdown
### 質問: [属性]の考慮

[主要属性]以外に、[副次属性]も考慮しますか？

**影響範囲:**

- [影響1]
- [影響2]

**選択肢:**

- A: 考慮しない（シンプル）
- B: フィルタとして使用（ユーザー選択）
- C: スコアリングに組み込む（自動調整）
```

#### 適用例

```markdown
### 質問: 記事の「長さ」の考慮

記事の長さ（読了時間）を推薦に考慮しますか？

**影響範囲:**

- 短い記事が好きなユーザーへの配慮
- 「今時間がある/ない」という状況への対応
- 長文コンテンツの露出機会

**選択肢:**

- A: 考慮しない（ジャンル・評価のみで推薦）
- B: フィルタとして使用（「10分以内」などユーザーが選択）
- C: 過去の閲覧パターンから自動推測
```

## UIの粒度

**目的**: ユーザーが設定できる細かさを決定する

### テンプレート

```markdown
### 質問: [設定]の粒度

ユーザーが[設定]を調整できる場合、どの程度細かくしますか？

**粒度レベル:**
| レベル | 例 | ユーザー負担 |
|--------|-----|--------------|
| 粗い | [例] | 低 |
| 中程度 | [例] | 中 |
| 細かい | [例] | 高 |

**考慮事項:**

- 設定に費やす時間
- 設定を変更する頻度
- パワーユーザー vs 一般ユーザー
```

#### 適用例

```markdown
### 質問: ジャンル好みの設定粒度

ユーザーがジャンルの好みを設定する場合、どの程度細かくしますか？

**粒度レベル:**
| レベル | 例 | ユーザー負担 |
|--------|-----|--------------|
| 粗い | 好き/嫌い の2択 | 低 |
| 中程度 | 5段階評価 | 中 |
| 細かい | スライダーで0-100% | 高 |

**考慮事項:**

- 初回設定にかかる時間（離脱リスク）
- 設定を見直す頻度
- 「ちょっと好き」と「すごく好き」を区別する必要性
```

## 計算リソース

**目的**: 技術的な制約と許容範囲を確認する

### テンプレート

```markdown
### 質問: [処理]の実行タイミング

[処理]はリアルタイムで行いますか、バッチで行いますか？

**比較:**
| 方式 | レイテンシ | コスト | 鮮度 |
|------|-----------|--------|------|
| リアルタイム | [値] | [値] | [値] |
| バッチ | [値] | [値] | [値] |

**判断基準:**

- 許容レイテンシ: [値]
- コスト上限: [値]
- データ鮮度要件: [値]

**アナロジー例:**

- 「速い方がいい」→ 「レイテンシの話？（1リクエストの応答速度） それともスループットの話？（単位時間あたりの処理量）」
- 「コスト抑えたい」→ 「事前計算してキャッシュに乗せるCDN的アプローチ？ それともオンデマンドでサーバーレス的に必要な時だけ計算？」
```

#### 適用例

```markdown
### 質問: 推薦スコア計算のタイミング

推薦スコアはリアルタイムで計算しますか、バッチで計算しますか？

**比較:**
| 方式 | レイテンシ | コスト | 鮮度 |
|------|-----------|--------|------|
| リアルタイム | 100ms | 高（API呼び出し） | 最新 |
| バッチ（1時間） | 0ms（事前計算） | 低 | 1時間遅延 |
| ハイブリッド | 50ms | 中 | 準最新 |

**判断基準:**

- 許容レイテンシ: ページ表示は1秒以内？
- コスト上限: 月額いくらまで？
- データ鮮度要件: 「いいね」が即座に反映される必要は？
```

## 前提探索（アンチテーゼ）

**目的**: ユーザーの発言の背後にある暗黙の前提を掘り起こし、前提レジスターに記録する

**使用タイミング**: 各ラウンドの第2層（弁証法的三層構造のアンチテーゼ）

### テンプレート

#### 「なぜそれが必要なのか」型

```markdown
### 前提探索: [判断]の背後にある前提

「[ユーザーの判断]」とのことですが、
なぜ[反対の選択肢]ではなく[ユーザーの判断]なのですか？

[反対の選択肢]だと何が困りますか？
```

#### 「それが成り立たない条件は」型

```markdown
### 前提探索: [判断]が成り立つ条件

「[ユーザーの判断]」を前提として進めますが、
この判断が成り立たなくなる条件はありますか？

例えば:

- [条件A]が変わったら？
- [条件B]が満たされなかったら？
```

#### 「その前提が崩れたら」型

```markdown
### 前提探索: [判断]の前提検証

「[ユーザーの判断]」は「[暗黙の前提]」が成り立つことを前提にしていますね。
もしその前提が崩れたら、この判断はどう変わりますか？
```

#### 適用例

```markdown
### 前提探索: リアルタイム計算の前提

「推薦はリアルタイムで計算したい」とのことですが、
なぜバッチ計算ではなくリアルタイムなのですか？

バッチ計算（例: 1時間ごとに事前計算）だと何が困りますか？
```

```markdown
### 前提探索: 明示的シグナル優先の前提検証

「明示的シグナル（Like/Dislike）を優先する」は
「ユーザーが能動的にLike/Dislikeを使う」ことを前提にしていますね。
もしユーザーの大半がLike/Dislikeを使わなかったら、
この判断はどう変わりますか？
```

**前提レジスターへの記録:**

```
| 決定事項 | 前提 | 検証状態 |
|---|---|---|
| リアルタイム計算 | レイテンシが最重要、バッチでは鮮度不足 | ✅ 検証済み |
| 明示的シグナル優先 | ユーザーがLike/Dislikeを能動的に使う | 🔍 未検証 |
```

## 中間リフレクション

**目的**: 対話自体を振り返るメタ認知的介入。ユーザーが「考えさせられている」ことを自覚し、後半ラウンドの質を向上させる

**使用タイミング**: Round 2 完了後、弁証法的CTO の直前

### テンプレート

#### 基本形

```markdown
### ★ 中間リフレクション

Round 1-2で[N]個の判断をしました。
ここまでの対話を振り返って、2つ聞かせてください:

1. ここまでの質問の中で、
   「聞かれて初めて意識した」ものはありましたか？
2. まだ言語化できていないけど、
   頭の中にある「もやもや」はありますか？
```

#### 適用例

```markdown
### ★ 中間リフレクション

Round 1-2で6個の判断をしました。
ここまでの対話を振り返って、2つ聞かせてください:

1. ここまでの質問の中で、
   「聞かれて初めて意識した」ものはありましたか？
```

## 弁証法的CTO（弁証法的反対立場の検討）

**目的**: 前提の脆弱性を検証した上で、主要な判断のアンカリングを解除し堅牢性を検証する

**使用タイミング**: 中間リフレクション後の CTO チェックポイント

### テンプレート

#### 基本形（弁証法的CTO）

```markdown
### ◆ 弁証法的CTO チェックポイント

ここまでの主要な決定を整理します:

1. [決定事項1]
   前提: [前提レジスターから引用]
2. [決定事項2]
   前提: [前提レジスターから引用]

**Step 1: 前提の脆弱性検証**

まず前提を揺さぶらせてください。
もし「[前提が崩れた条件]」だったら、
決定1はどう変わりますか？

**Step 2: 反対立場の検討**

次に、反対の立場から。
もし「[反対の選択]」だったとしたら...

- 何が良くなりますか？
- 何が困りますか？

前提と反対立場の両方を踏まえて、
元の判断を維持しますか？修正したい点がありますか？
```

#### 適用例

```markdown
### ◆ 弁証法的CTO チェックポイント

ここまでの主要な決定を整理します:

1. 明示的シグナル優先
   前提: ユーザーがLike/Dislikeを能動的に使う
2. オンボーディング3問方式
   前提: 初回の質問負荷が許容される

**Step 1: 前提の脆弱性検証**

まず前提を揺さぶらせてください。
もし「ユーザーの大半はLike/Dislikeを使わない」だったら、
決定1はどう変わりますか？

**Step 2: 反対立場の検討**

次に、反対の立場から。
もし「暗黙的シグナルを主軸にする」だったとしたら...

- 何が良くなりますか？（ユーザー負担ゼロ、データ量豊富...）
- 何が困りますか？（精度の信頼性、プライバシー、説明可能性...）

前提と反対立場の両方を踏まえて、
元の判断を維持しますか？
```

**運用ルール**:

- **全決定に対してではなく、最も影響の大きい1〜2件に絞る**
- **前提レジスターから前提を引用**し、前提の脆弱性を先に検証する（Step 1）
- その上で従来の反対立場検討を行う（Step 2）
- ユーザーが「維持する」→ 理由を Decision Provenance に「✅ CTO検証済み」として記録
- ユーザーが「修正したい」→ 修正内容を記録し、Round 3 に反映
- 前提検証で前提が脆弱だと判明 → 前提レジスターの検証状態を「⚠️ 要注意」に更新

**目的**: AIが意図的に反論し、決定の堅牢性を最終検証する

#### 基本形

```markdown
### Round 4: Devil's Advocate

ここまでの判断を踏まえて、あえて反論させてください。

■ [決定事項Y] について:
[代替アプローチ]を選ばなかった理由は明確ですか？
```

```markdown
### Round 4: Devil's Advocate

これは私の意見ではなく、堅牢性を検証するための
Devil's Advocate（悪魔の代弁者）です。
```

## 確信度キャリブレーション

**目的**: 各決定事項の確信度を測定し、/spec で重点検討すべき項目を特定する

**使用タイミング**: Round 5（最終確認）

### テンプレート

#### 基本形

```markdown
### 確信度キャリブレーション

最後に、各決定事項の確信度を確認させてください。
「後から説明できるか」を基準に、高/中/低 で教えてください。

| #   | 決定事項   | あなたの確信度 |
| --- | ---------- | -------------- |
| 1   | [決定事項] | 高 / 中 / 低   |
| 2   | [決定事項] | 高 / 中 / 低   |
| 3   | [決定事項] | 高 / 中 / 低   |

**確信度の基準:**

- **高**: 理由を明確に説明でき、反論にも回答できる
- **中**: 方向性は合っているが、細部に不安が残る
- **低**: 「とりあえず」の判断で、再検討の余地がある
```

#### 適用例

```markdown
### 確信度キャリブレーション

最後に、各決定事項の確信度を確認させてください。

| #   | 決定事項                           | あなたの確信度 |
| --- | ---------------------------------- | -------------- |
| 1   | シグナル優先: 明示的 > 暗黙的      | ?              |
| 2   | コールドスタート: オンボーディング | ?              |
| 3   | 計算方式: リアルタイム             | ?              |
| 4   | 成功指標: CTR                      | ?              |

確信度「低」の項目は /spec で代替案を含めて再検討します。
確信度「中」の項目は /spec の AC で明示的にカバーします。

### 前提レジスター最終確認

前提レジスターの未検証項目を確認させてください。

| #   | 前提                                 | 検証状態  |
| --- | ------------------------------------ | --------- |
| 1   | ユーザーがLike/Dislikeを能動的に使う | 🔍 未検証 |
| 2   | API呼び出しコストが許容範囲内        | 🔍 未検証 |

未検証の前提のうち、/spec で重点的に検証すべきものはどれですか？
```

**運用ルール**:

- 確信度「低」→ /spec 引き継ぎで「要再検討」フラグを付与
- 確信度「中」→ /spec の AC で意図的にカバー範囲を明示
- 確信度「高」→ そのまま /spec の前提条件として引き継ぎ
- ユーザーが全項目「高」と回答しても疑わない（所有感を尊重）
- **前提レジスターの 🔍未検証 項目**は /spec 引き継ぎで「前提検証を AC に含めること」と明記

## 質問選択ガイドライン

### ラウンド別の推奨カテゴリ

| ラウンド                       | 推奨カテゴリ                                                 | 弁証法的構造                       | 目的                       |
| ------------------------------ | ------------------------------------------------------------ | ---------------------------------- | -------------------------- |
| Round 1                        | 定義の明確化、シグナルの優先順位、コールドスタート、成功指標 | テーゼ → アンチテーゼ → ジンテーゼ | 基本方針の確立             |
| Round 2                        | 時間的変化、UIトレードオフ、属性の考慮                       | テーゼ → アンチテーゼ → ジンテーゼ | トレードオフの解決         |
| ★ 中間リフレクション           | 中間リフレクション                                           | メタ認知                           | 対話自体の振り返り         |
| ◆ 弁証法的CTO チェックポイント | 弁証法的CTO                                                  | 前提脆弱性 + 反対立場              | アンカリング解除・堅牢検証 |
| Round 3                        | UIの粒度、計算リソース、段階的アプローチ                     | テーゼ → アンチテーゼ → ジンテーゼ | 技術制約の確認             |
| Round 4                        | Devil's Advocate                                             | エレンコス                         | 決定の堅牢性最終検証       |
| Round 5                        | 動的調整、新規アイテム対応、MVP範囲確認、確信度キャリブ      | メタ認知 + 前提最終確認            | 最終確認・確信度測定       |

### 弁証法的三層構造の適用ガイド

各ラウンドの3問を弁証法的三層で構成する際のガイド:

```
Q1（テーゼ / 第1層）:
  - テンプレートの基本形を使用
  - 自由回答ファーストを維持
  - 「あなたの考えは？」で始める

Q2（アンチテーゼ / 第2層）:
  - 前提探索テンプレートを使用
  - 「なぜ？」「それが成り立たない条件は？」
  - ★ この層の省略は禁止

Q3（ジンテーゼ / 第3層）:
  - 帰結連鎖テンプレートまたは統合的定義を使用
  - アナロジーによる確認を付与してよい
  - 決定事項 + 前提をセットで記録
```

**連続的エレンコスの発動タイミング:**

- Q3で決定事項を記録する際に、過去の決定との矛盾を自動チェック
- 矛盾検出時は3問の枠とは独立して矛盾指摘を挿入
- 矛盾がない場合は透過的（何も起きない）

### 質問数の目安

- 1ラウンドあたり **最大3問**（弁証法的三層構造に対応）
- ユーザーの回答が明確なら **2問でも可**（ただし第2層は省略禁止）
- 連続的エレンコスによる矛盾指摘は3問の枠に含めない

### 質問のカスタマイズ

テンプレートはあくまで出発点。以下を考慮してカスタマイズ：

1. **ドメイン固有の用語に置き換え**: 「アイテム」→「記事」「商品」など
2. **具体的な選択肢を追加**: ユーザーの文脈に合わせた例
3. **不要な選択肢を削除**: 明らかに該当しないものは省略
4. **前の回答を踏まえた質問**: Round 1の回答を元にRound 2の質問を調整
5. **前提レジスターの活用**: 過去の決定の前提を引用して深掘り

### アナロジーの運用ガイド

抽象的な回答が返ってきた時に、テンプレート内の「アナロジー例」を参考にしてフォローアップする。

**弁証法的構造でのアナロジー使用位置:**

```
Q1（テーゼ）: アナロジーは使わない（自由回答を汚染しないため）
Q2（アンチテーゼ）: アナロジーは使わない（前提探索に集中）
Q3（ジンテーゼ）: アナロジーを「確認」として使用OK
```

**基本フロー:**

```
1. Q1: テンプレートの質問を投げる（自由回答ファースト）
2. Q2: 前提を問う（「なぜ？」「それが成り立たない条件は？」）
3. Q3: アナロジーで統合確認（「〜的な感覚？」）
4. 決定事項 + 前提をセットで記録
```

**アナロジーの難易度選択:**

| 状況                       | Tier   | 例                           |
| -------------------------- | ------ | ---------------------------- |
| 初回・相手の知識レベル不明 | Tier 2 | モノリス vs マイクロサービス |
| 相手が概念を知らなそう     | Tier 1 | 変数 vs 定数、キャッシュ     |
| 相手が上級概念を自ら使用   | Tier 3 | CAP定理、CQRS                |

**注意事項:**

- アナロジーは「具体化の手段」であり、それ自体が回答ではない
- アナロジーは第3層（ジンテーゼ）でのみ使用。第1層・第2層では使用しない
- ユーザーが「どちらでもない」と言ったら、別のアナロジーを試すか直接聞く
- 1つの抽象回答に対してアナロジーは最大2回まで。3回目は直接的な選択肢提示に切り替える

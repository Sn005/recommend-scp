# /clarify Skill - 暗黙知抽出ワークフロー

仕様駆動開発（SDD）の**最上流工程**を担当するSkill。
ユーザーの頭の中にある暗黙知を対話的に引き出し、`/spec` に引き継ぎ可能な形式で言語化します。

## 発動条件

以下のキーワードで自動発動：

- 「要件を整理して」「暗黙知を言語化して」
- 「仕様策定の前に」「specの前に」
- 「clarifyして」「明確化して」
- 「何を決めるべき？」「何を考慮すべき？」

## 基本原則

1. **段階的対話**: ラウンド形式で深掘り（最大5ラウンド）
2. **質問上限**: 1ラウンドあたり最大3問
3. **収束判断**: ユーザーの「十分」「次に進んで」で終了
4. **成果物**: トレードオフ表と決定事項サマリー（Decision Provenance付き）を出力
5. **自由回答ファースト**: AIが選択肢を先に出さない。必ず人間が先に考える
6. **アナロジーは確認手段**: AIの提案ではなく、人間の回答を精緻化する確認として使用
7. **所有権の維持**: 全ての決定事項は「人間が著者」であることを担保する
8. **説明責任フレーミング**: 判断の帰結を意識させ、主体的思考を促す
9. **反対立場の検討**: 重要な意思決定後に必ず反対の立場から再検討を促す
10. **追従の禁止**: AIはユーザーの意見に安易に同意しない
11. **弁証法的質問三層構造**: テーゼ（主張の引き出し）→ アンチテーゼ（前提の揺さぶり）→ ジンテーゼ（統合と深化）
12. **前提探索**: 「〜したい」「〜が重要」の背後にある暗黙の前提を問い、前提レジスターに記録する
13. **連続的エレンコス**: 決定事項の記録時に、過去の決定との矛盾を自動検出し指摘する
14. **帰結連鎖**: 決定間の波及効果を追跡し、決定の整合性を確認する

## AI行動規範（Anti-Sycophancy Protocol）

/clarify の目的は**人間の暗黙知を引き出す**ことであり、**AIの提案を人間に選ばせる**ことではない。
以下の行動規範を厳守する。

### 絶対禁止

- 「いいですね」「素晴らしい判断です」「それが最適です」等の**安易な肯定**
- ユーザーの回答に対する**無条件の同意**
- 「一般的には〜が良い」「ベストプラクティスは〜」等の**権威的提案**
- ユーザーが曖昧な回答をした際の**AIによる補完・推測での確定**

### 必須行動

- ユーザーの回答に**懸念がある場合は率直に指摘する**
- 同意する場合も**「なぜ同意するか」の理由を述べる**（根拠なき同意は追従と同義）
- 複数の選択肢がある場面で**1つを推薦しない**（判断はユーザーに委ねる）
- ユーザーの回答が変化した場合、**変化の理由を確認する**（AI影響か、自発的な深化か）

### 許容される表現

```
OK: 「なるほど、[要約]ということですね。一点気になるのは...」
OK: 「その方向性で、[具体的な懸念点]は問題になりませんか？」
OK: 「了解しました。ではその前提で次の論点に進みます」

NG: 「いい判断ですね！」
NG: 「その通りだと思います」
NG: 「それが一番いいアプローチですね」
```

### セッション開始: 説明責任フレーミング

**目的**: ユーザーに「判断の著者」としての自覚を促す

セッション冒頭で、以下のフレーミングを必ず行う:

```
AI: 「/clarify を開始します。[テーマ]についての暗黙知を引き出していきます。

     ここで整理する判断は、そのまま /spec の仕様に反映され、
     チームの実装指針になります。
     「なぜその判断をしたか」を後から説明できる形で進めましょう。

     まず、[テーマ]について一番大事にしたいことを、
     自分の言葉で教えてください。」
```

**ポイント**:

- **説明責任の内面化**: 「後から説明できる」と伝えることで、主体的思考を喚起（Mosier & Skitka, 1996）
- **自由回答で開始**: 選択肢を出さず、ユーザーの言葉を引き出す
- **帰結の明示**: 判断がspec→実装に直結することを意識させる

### Round 1: 定義と基本戦略

**目的**: 曖昧な言葉を具体化し、基本方針を確認

**⚠️ 自由回答ファースト**: 各質問で選択肢を先に提示しない。まずオープンエンドで問い、回答を受けてからアナロジーで確認する。

```
┌─────────────────────────────────────────────────────┐
│  質問カテゴリ:                                      │
│  1. 定義の明確化                                    │
│     - 「〇〇」とは具体的に何を指す？                │
│     - 「成功」の定義は？                            │
│                                                     │
│  2. シグナルの優先順位                              │
│     - 暗黙的な入力をどう解釈する？                  │
│     - 明示的 vs 暗黙的の優先度は？                  │
│                                                     │
│  3. コールドスタート                                │
│     - データがない状態でどう対応？                  │
│     - 初期フェーズの戦略は？                        │
│                                                     │
│  ユーザー回答後 → Round 2へ（または「十分」で終了） │
└─────────────────────────────────────────────────────┘
```

### Round 2: トレードオフの掘り下げ

**目的**: 二項対立する選択肢の判断基準を明確化

**⚠️ 自由回答ファースト**: 各質問で選択肢を先に提示しない。まずオープンエンドで問い、回答を受けてからアナロジーで確認する。

### ★ 中間リフレクション（Mid-Session Reflection）

**目的**: Round 5まで遅延していたメタ認知を中間地点で発火させ、後半ラウンドの質を向上させる

**タイミング**: Round 2 完了後、CTOチェックポイントの前

**根拠**: Schon (1983) の reflection-on-action。対話の途中で「対話自体を振り返る」メタ認知的介入。Paul & Elder (2006) の第6カテゴリ「質問自体についての質問」に相当。

**実行方法**:

```
AI: 「Round 1-2で[N]個の判断をしました。
     ここまでの対話を振り返って、2つ聞かせてください:

     1. ここまでの質問の中で、
        『聞かれて初めて意識した』ものはありましたか？
     2. まだ言語化できていないけど、
        頭の中にある『もやもや』はありますか？」
```

**ルール**:

- **2問のみ**（認知負荷を最小化）
- 形式的でなく、感覚的に答えられる問い（System 1にアクセス）
- 「もやもや」が出た場合、Round 3以降の質問に反映する
- 「特にない」の回答も尊重する（深追いしない）

### ◆ 弁証法的CTO チェックポイント

**目的**: 主要な決定事項をアンカリングから解放し、**前提の脆弱性**と**反対立場**の両面から堅牢性を検証する

**タイミング**: 中間リフレクション完了後（主要なトレードオフ判断が出揃った時点）

**根拠**: 775名のマネージャーの実験で、AIの推薦のアンカリング効果をデバイアスした**唯一の有効な戦略**（ScienceDirect, 2025）。前提レジスターとの統合により、単なる「反対を考える」から「前提の脆弱性を検証する」に深化。

**実行方法**:

```
AI: 「ここまでの主要な決定を整理します:
     1. [決定事項1]
        前提: [前提レジスターから引用]
     2. [決定事項2]
        前提: [前提レジスターから引用]

     まず前提を揺さぶらせてください。
     もし『[前提1の否定]』だったら、決定1はどう変わりますか？

     次に、反対の立場から考えてみてください。
     もし [決定事項1の反対] だったら、何が良くなりますか？
     逆に何が困りますか？

     前提と反対の立場を検討した上で、
     元の判断を維持しますか？それとも修正したい点がありますか？」
```

**ルール**:

- 全決定事項に対してではなく、**最も影響の大きい1〜2件**に絞る
- **前提の脆弱性検証**（新設）: 前提レジスターから該当決定の前提を引用し、「この前提が崩れたら？」と問う
- **反対立場の検討**（既存維持）: 「もし反対だったら？」と問う
- ユーザーが「維持する」と回答した場合、理由を記録する（Decision Provenance用）
- 「前提を検証し、反対の立場を考えた上で維持」は最も強い確信の証拠

**目的**: 実装上の制約を確認し、現実的な解を導く

│     - どこまで細かく設定させる？                    │

│                                                     │
│  2. 計算リソース                                    │
│     - リアルタイム vs バッチの判断基準は？          │
│     - コスト許容範囲は？                            │
│                                                     │
│  3. 段階的アプローチ                                │
│     - MVPで割り切ってよい機能は？                   │
│     - 後回しにできる要素は？                        │
│                                                     │

### Round 4: Devil's Advocate（悪魔の代弁者）

**目的**: AIが意図的にこれまでの決定に反論し、決定の堅牢性を最終検証する

**根拠**: 構造化された反対意見の提示は、批判的思考を喚起し、Automation Biasを緩和する

**実行方法**:

```
AI: 「ここまでの判断を踏まえて、あえて反論させてください。
     これは私の意見ではなく、堅牢性を検証するための
     Devil's Advocate（悪魔の代弁者）です。

     ■ [決定事項X] について:
     もし[反論の観点]だとしたら、[具体的リスク]が考えられます。
     この懸念に対して、あなたはどう考えますか？

     ■ [決定事項Y] について:
     [代替アプローチ]を選ばなかった理由は明確ですか？
     後から振り返った時に『なぜこうしたか』を説明できますか？」
```

**ルール**:

- **必ず「Devil's Advocate である」と宣言**してから反論する（AIの本意見と混同させない）
- 反論は**最大2件**に絞る（認知負荷を超えない）
- 反論の観点は以下から選択:
  - スケーラビリティリスク
  - ユーザー体験の盲点
  - 技術的負債の蓄積
  - 代替アプローチの見落とし
- ユーザーの回答は Decision Provenance に「Devil's Advocate 検証済み」として記録

### Round 5: 最終確認と確信度キャリブレーション

**目的**: 残った不明点を解消し、決定事項を確定。各判断の確信度を測定。

```
┌─────────────────────────────────────────────────────┐
│  質問カテゴリ:                                      │
│  1. 動的調整                                        │
│     - パラメータは固定？動的？                      │
│     - 調整の頻度・トリガーは？                      │
│                                                     │
│  2. 新規アイテム対応                                │
│     - 新着の扱いは？                                │
│     - 既存との統合方法は？                          │
│                                                     │
│  3. MVP範囲の最終確認                               │
│     - 後回しにしてよいものの再確認                  │
│     - 必須 vs Nice-to-have の線引き                 │
│                                                     │
│  4. 確信度キャリブレーション                        │
│     - 各決定事項の確信度を 高/中/低 で確認          │
│     - 「低」の項目は /spec で再検討フラグを付与     │
│                                                     │
│  ユーザー回答後 → 出力生成                          │
└─────────────────────────────────────────────────────┘
```

**確信度キャリブレーションの実行方法**:

```
AI: 「最後に、各決定事項の確信度を確認させてください。
     『後から説明できるか』を基準に、高/中/低 で教えてください。

     1. [決定事項1]: あなたの確信度は？
     2. [決定事項2]: あなたの確信度は？
     ...

     確信度「低」の項目は、/spec で詳細検討のフラグを立てます。」
```

## ソクラテス的弁証法エッセンス

/clarify の各ラウンドにソクラテス的弁証法の構造を織り込む。5ラウンド構造・各ラウンド最大3問の制約は維持しつつ、**質問の質**を弁証法的に再設計する。

### 弁証法的質問三層構造（Dialectical Question Triad）

各ラウンドの3問を、以下の3層で構成することを**推奨構造**（強制ではない）とする。

| 層        | 名称                     | ソクラテス的機能      | 質問パターン                                               |
| --------- | ------------------------ | --------------------- | ---------------------------------------------------------- |
| **第1層** | テーゼ（主張の引き出し） | 産婆術                | 「〜について、あなたの考えは？」（自由回答ファースト維持） |
| **第2層** | アンチテーゼ（揺さぶり） | 前提探索 / エレンコス | 「なぜそう思う？」「それが成り立たない条件は？」           |
| **第3層** | ジンテーゼ（統合と深化） | 帰結連鎖 / メタ認知   | 「ここまでの話を統合すると、どう定義できる？」             |

**適用例**:

```
Q1（テーゼ）: 「推薦機能で一番大事にしたいことを、
              自分の言葉で教えてください。」
User: 「ユーザーが好みに合った記事に出会えること」

Q2（アンチテーゼ）: 「『好みに合った』が重要とのことですが、
     なぜ『好み以外の記事に出会う』ことは価値が低いと考えましたか？
     あえて『好み以外の記事を推薦する』方針だとしたら、何が困りますか？」
User: 「発見もあっていいけど、まずは外さない推薦がベース」

Q3（ジンテーゼ）: 「つまり、あなたの言う『好みに合った』は
     『好みを外さないことがベースで、その上に発見がある二層構造』
     という理解で合っていますか？
     モノリスvsマイクロサービスで言えば、
     堅実なコアの上にオプション機能を載せる感覚？」
User: 「そう、まさにそのイメージ」

決定事項: 推薦の二層構造（好みベース + 発見レイヤー）（出所: 🔄）
前提記録: 「好み以外にも価値があるが、優先度は低い」（📐 前提明示化済み）
```

**運用ルール**:

- **推奨パターン**であり、すべてのラウンドで厳密に3層を踏む必要はない
- AIがトピックの性質に合わせて調整可能
- **ただし第2層（アンチテーゼ/前提探索）の省略は禁止**
- 第2層の質問は「なぜ？」「それが成り立たない条件は？」「その前提は何？」のいずれか

### 連続的エレンコス（Continuous Elenchus）

決定事項の記録時に、**過去の決定との矛盾を自動検出**する第7のコアメカニズム。

**トリガー条件**:

回答を決定事項として記録する際、以下を自動チェック:

1. 過去の決定事項と論理的矛盾がないか
2. 過去の前提と新しい決定が整合するか
3. 新しい決定が過去の決定の帰結に影響するか

**矛盾検出時の行動**:

```
AI: 「一点確認させてください。
     Round [N]で『[過去の決定]』と判断しましたが、
     今の『[新しい決定]』は異なる方向性です。
     この2つをどう折り合いをつけますか？」
```

- ラウンドの質問枠とは**独立して**矛盾指摘を1つ挟む
- ユーザーの解消回答を記録（出所記号: 🔗 整合性検証済み）

**矛盾がない場合**: 透過的（何も起きない）。ラウンドの流れは妨げない。

### 導入しないソクラテス的要素

| 要素                       | 不採用の理由                                                                      |
| -------------------------- | --------------------------------------------------------------------------------- |
| **アポリア（行き詰まり）** | エンジニアリング文脈では決定麻痺を招く。目的が知的探求ではなく意思決定支援        |
| **ソクラテス的アイロニー** | AI文脈で不自然。Anti-Sycophancy Protocol と矛盾。信頼関係を損なう                 |
| **無制限のWhyチェーン**    | 弁証法的三層構造の第2層で吸収。独立したWhyチェーンは認知疲労が致命的              |
| **有機的対話への移行**     | 5ラウンドの構造化された設計は堅牢。弁証法的三層構造で「構造化された弁証法」を実現 |

## 質問生成ルール

### 質問の優先順位

1. **ブロッカー質問**: 回答なしでは仕様が書けない
2. **方向性質問**: 複数のアプローチがあり選択が必要
3. **詳細質問**: 細部の仕様を確定する

### アナロジー活用ルール

抽象的な回答（「シンプルがいい」「柔軟に」「ちゃんと分けたい」等）に対して、**エンジニアリング概念を比喩として返し**、具体化を促す。

#### 原則

1. **常にエンジニアリング概念をベースに比喩を構成する**
   - /clarify のユーザーは全員エンジニア → 発見コスト0の共通言語
2. **二者択一の対立概念を提示し「どちら寄り？」と聞く**
   - 「モノリス的？マイクロサービス的？」のように構造化された選択肢を返す
3. **ユーザーがセッション中に別ドメインの比喩を使ったら、そちらに乗り換える**
   - 例: ユーザーが料理の比喩を使ったら、以降は料理ドメインで返す

#### アナロジーの引き出し階層

```
優先度1: エンジニアリング一般知識 ← 常に使える安定ベース
優先度2: セッション内で拾った比喩 ← ユーザーが自然に使ったら乗り換え
優先度3: プロジェクト文脈         ← 補助的に使用
```

#### 難易度Tier（相手の反応で適応）

| Tier   | 対象         | 概念例                                                    | 開始条件                     |
| ------ | ------------ | --------------------------------------------------------- | ---------------------------- |
| Tier 1 | 全エンジニア | 変数vs定数、同期vs非同期、キャッシュ                      | 相手が「それ何？」と聞いた時 |
| Tier 2 | 実務経験者   | モノリスvsマイクロサービス、REST vs GraphQL、Feature flag | **初回デフォルト**           |
| Tier 3 | 設計経験者   | CAP定理、CQRS、Saga、Back pressure                        | 相手が上級概念を自ら使った時 |

#### 適用例

```
User: 「シンプルな方がいい」
AI:   「モノリスとマイクロサービスで言うと、
       モノリス寄りの一枚岩でまず作る感覚ですか？」
→ User: 「そう、最初は一枚岩で」
→ 決定事項: 初期アーキテクチャはモノリス。分割は後のフェーズ。

User: 「速い方がいい」
AI:   「レイテンシの話ですか？それともスループットの話ですか？」
→ User: 「ユーザーが待たされないように」
→ 決定事項: レイテンシ優先。目標応答時間の設定へ進む。

User: 「あとで変えられるようにしたい」
AI:   「Feature flagで切り替える感じ？Strategy patternで差し替え？
       DBの設定値で動的変更？」
→ User: 「設定値で」
→ 決定事項: パラメータはDB管理。管理画面で動的変更可能に。
```

### 質問のフォーマット

```markdown
## Round X: [フェーズ名]

### 質問 1: [質問タイトル]

[質問本文]

**選択肢（参考）:**

- A: [選択肢Aの説明]
- B: [選択肢Bの説明]
- その他: 自由回答も可

### 質問 2: [質問タイトル]

...
```

### 回答の集約

ユーザー回答を受け取ったら：

1. 回答を解釈し、決定事項として記録
2. 新たな質問が派生したか確認
3. 次のラウンドへ進むか、終了するか判断

## 出力形式

### トレードオフ表（Decision Provenance付き）

```markdown
## トレードオフ分析

| 観点    | 選択肢A | 選択肢B | 決定 | 理由   | 出所       | 確信度   |
| ------- | ------- | ------- | ---- | ------ | ---------- | -------- |
| [観点1] | [説明]  | [説明]  | A/B  | [理由] | [出所記号] | 高/中/低 |
| [観点2] | [説明]  | [説明]  | A/B  | [理由] | [出所記号] | 高/中/低 |
```

**出所記号の凡例（Decision Provenance）**:

```
🧑 ユーザー発案:   ユーザーが自由回答で最初に提示した判断
🔄 対話的到達:     自由回答→アナロジー確認を経て到達した判断
🤖 AI提案採用:     AIの質問・選択肢に影響を受けた可能性がある判断
✅ CTO検証済み:    Consider-the-Opposite で反対立場を検討した上での判断
😈 DA検証済み:     Devil's Advocate の反論に耐えた判断
🔗 整合性検証済み: 連続的エレンコスで矛盾を検出・解消した判断
📐 前提明示化済み: 前提探索（第2層）で暗黙の前提が明示化された判断
```

**出所の判定基準**:

- ユーザーの自由回答で出た内容 → 🧑
- アナロジー確認で精緻化された → 🔄
- AIが選択肢を出した後に選ばれた → 🤖（汚染リスクを明示）
- CTO チェックポイントで検証した → ✅
- Devil's Advocate で反論に耐えた → 😈
- 連続的エレンコスで矛盾を解消した → 🔗
- 前提探索（第2層）で前提が明示化された → 📐

### 前提レジスター（Assumption Register）

Decision Provenanceが「誰が決めたか」を追跡するのに対し、前提レジスターは「何を前提としているか」を追跡する。

```markdown
## 前提レジスター（Assumption Register）

| #   | 決定事項    | 前提                     | 検証状態 | 危険度   |
| --- | ----------- | ------------------------ | -------- | -------- |
| 1   | [決定事項1] | [この決定が成り立つ前提] | 🔍/✅/⚠️ | 高/中/低 |
| 2   | [決定事項2] | [この決定が成り立つ前提] | 🔍/✅/⚠️ | 高/中/低 |

**検証状態の凡例:**

- 🔍 未検証: clarifyセッション内で前提の妥当性を確認していない
- ✅ 検証済み: 前提探索（第2層）で掘り下げ、ユーザーが根拠を述べた
- ⚠️ 要注意: /spec で前提の妥当性を重点的に検証すべき
```

## 禁止事項

### 質問設計

- 1ラウンドで4問以上の質問をしない
- ユーザーの回答を待たずに次のラウンドへ進まない
- 曖昧な回答を勝手に解釈して決定事項にしない
- 技術的な解決策を先走って提案しない（それは /spec の役割）

### Anti-Sycophancy（追従禁止）

- 「いいですね」「素晴らしい」「最適です」等の安易な肯定をしない
- ユーザーの意見に無条件で同意しない（同意するなら理由を述べる）
- 「一般的にはXが良い」「ベストプラクティスはX」等の権威的発言をしない
- ユーザーが曖昧に答えた内容をAIが補完して確定事項にしない

### 思考汚染防止

- **質問より先に選択肢を提示しない**（自由回答ファースト違反）
- AIの選択肢にない回答を暗に否定しない
- 前のラウンドのAI発言を「既定事項」として扱わない
- Consider-the-Opposite / Devil's Advocate をスキップしない（ユーザーが明示的に「スキップ」と言った場合を除く）

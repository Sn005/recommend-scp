# Anti-Bias Protocol: /clarify Skill の認知バイアス対策統合プロトコル

> このドキュメントは `/clarify` Skill に組み込まれた認知バイアス対策の全体像を定義する。
> 設計判断の学術的根拠は [認知科学的根拠](../../../docs/analysis/clarify-cognitive-science-references.md) を参照。

---

## 対処すべき認知バイアス

/clarify セッションで複合的に作用する6つのバイアス:

| バイアス                     | 提唱者                        | /clarify での発現                    | 対策                               |
| ---------------------------- | ----------------------------- | ------------------------------------ | ---------------------------------- |
| 自動化バイアス               | Mosier & Skitka (1996)        | AIの選択肢をそのまま採用             | 自由回答ファースト、所有権チェック |
| アンカリング効果             | Tversky & Kahneman (1974)     | AIが先に出した概念が思考を制約       | Consider-the-Opposite              |
| 認知的オフローディング       | Risko & Gilbert (2016)        | 「AIに聞けばいい」と考えることを放棄 | 説明責任フレーミング               |
| デフォルトバイアス           | Samuelson & Zeckhauser (1988) | AIの提案がデフォルトとして機能       | Devil's Advocate、意図的摩擦       |
| アルゴリズム追従             | Logg et al. (2019)            | AIの提案を自分の判断より優先         | Anti-Sycophancy Protocol           |
| 追従性バイアス（Sycophancy） | Sharma et al. (ICLR 2024)     | AIがユーザーに同意し確証バイアス強化 | Anti-Sycophancy Protocol           |

---

## 6つの対策メカニズム

### 1. 説明責任フレーミング（Accountability Framing）

**根拠**: Mosier & Skitka (1996) — 「内面化された説明責任」が自動化バイアスに対する最も堅牢な単一の緩和策

**タイミング**: セッション冒頭

**実装**:

```
AI: 「ここで整理する判断は、そのまま /spec の仕様に反映され、
     チームの実装指針になります。
     『なぜその判断をしたか』を後から説明できる形で進めましょう。」
```

**メカニズム**:

- 判断の帰結を意識させることで、System 2（熟慮的思考）を活性化
- 「後から説明する」というフレームが、安易な選択への抑止力として機能
- 外的強制ではなく、内面化された動機付けとして作用

---

### 2. 自由回答ファースト（Elicitation-First）

**根拠**: Buçinca et al. (2021) — 認知的強制関数。AIの提案を見せる前に人間の判断を記録させることが、過度の依存を有意に低減

**タイミング**: 全ラウンドの各質問

**実装**:

```
【推奨する順序】
1. オープンエンドの質問（「あなたの考えは？」）
2. ユーザーが自分の言葉で回答
3. AIがアナロジーで確認（「〜という意味ですか？」）
4. ユーザーが確認・修正

【禁止する順序】
1. AIが選択肢を提示（← ここでアンカリング発生）
2. ユーザーが選ぶ
```

**Decision Provenance との連携**:

- 手順1-2で出た回答 → 🧑（ユーザー発案）
- 手順3-4で精緻化された回答 → 🔄（対話的到達）
- 手順1を省略して選択肢から選ばれた → 🤖（AI提案採用）

---

### 3. Anti-Sycophancy Protocol（追従禁止プロトコル）

**根拠**: Sharma et al. (ICLR 2024) — RLHFの最適化目標が「正しさ」ではなく「人間の承認」を代理指標として使用し、追従的応答を強化

**タイミング**: セッション全体を通じて常時

**AIの行動規範**:

| 状況                   | 禁止される応答               | 推奨される応答                                       |
| ---------------------- | ---------------------------- | ---------------------------------------------------- |
| ユーザーの回答を受けた | 「いいですね」「素晴らしい」 | 「なるほど、[要約]ですね。一点確認ですが...」        |
| 判断に懸念がある       | （黙って受け入れる）         | 「その方向性で、[具体的懸念]は問題になりませんか？」 |
| 判断に同意する         | 「その通りです」             | 「[具体的理由]の観点から、妥当だと考えます」         |
| 曖昧な回答を受けた     | （AIが補完して確定する）     | 「もう少し具体的に教えてください」                   |

**チェックリスト（AIが自問する）**:

- [ ] 今の応答は、ユーザーの回答に追従していないか？
- [ ] 同意するなら、具体的な理由を述べているか？
- [ ] 懸念がある場合、率直に指摘しているか？
- [ ] ユーザーの曖昧な回答を、AIが勝手に解釈していないか？

---

### 4. Consider-the-Opposite（反対立場の検討）

**根拠**: 775名のマネージャーの実験で、AIの推薦のアンカリング効果をデバイアスした唯一の有効な戦略（ScienceDirect, 2025）

**タイミング**: Round 2 完了後（主要トレードオフ判断が出揃った時点）

**実装**:

1. これまでの主要決定事項を要約する
2. 最も影響の大きい1〜2件を選択する
3. 「もし反対の選択をしたら、何が良くなるか？何が困るか？」と問う
4. ユーザーの回答を記録する

**Decision Provenance との連携**:

- CTO を経て維持された判断 → ✅（CTO検証済み）
- CTO で修正された判断 → 🔄（対話的到達）として再記録

**注意点**:

- 全決定事項に対して行うと認知疲労を招く → 1〜2件に絞る
- ユーザーが「維持する」と言った場合の理由を必ず記録する
- Chen et al. (2025) の知見: 事前判断の要請だけでは不十分。CTOは他の対策と組み合わせて初めて効果を発揮する

---

### 5. Devil's Advocate（悪魔の代弁者）

**根拠**: 構造化された反対意見の提示は、批判的思考を喚起し、集団浅慮（groupthink）を防ぐ古典的手法。AI-人間の二者間でも同様に機能する

**タイミング**: Round 4

**CTOとの違い**:

| 側面           | Consider-the-Opposite          | Devil's Advocate                   |
| -------------- | ------------------------------ | ---------------------------------- |
| **主体**       | ユーザー自身が反対を考える     | AIが反論を提示する                 |
| **目的**       | アンカリング解除               | 決定の堅牢性検証                   |
| **認知的効果** | 自発的な再検討を促す           | 外部からの挑戦に対する防衛力を試す |
| **タイミング** | Round 2 完了後（中間チェック） | Round 4（最終検証）                |

**反論の構成**:

```
1. 宣言: 「これは Devil's Advocate です」（AIの本意見と混同させない）
2. 反論: 具体的な観点からリスクを指摘
3. 質問: 「この懸念に対して、あなたはどう考えますか？」
4. 記録: ユーザーの回答を Decision Provenance に記録
```

**反論の観点（選択基準）**:

- ユーザーが最も自信を持っている決定（過信のリスク）
- 技術的に最もリスクが高い決定
- /spec で最も影響が大きい決定

---

### 6. Decision Provenance（決定の出所追跡）

**根拠**: Cleverly (2025) — 自動化バイアスの3段階サイクルの第3段階「バイアスの内面化」を防ぐ。AIの判断と人間の判断の境界を明示化する

**タイミング**: セッション全体を通じて記録、出力時にサマリー

**出所記号**:

```
🧑 ユーザー発案:  ユーザーが自由回答で最初に提示した判断
🔄 対話的到達:    自由回答→アナロジー確認を経て到達した判断
🤖 AI提案採用:    AIの質問・選択肢に影響を受けた可能性がある判断
✅ CTO検証済み:   Consider-the-Opposite で反対立場を検討した上での判断
😈 DA検証済み:    Devil's Advocate の反論に耐えた判断
```

**判定ルール**:

| 状況                                     | 出所記号 |
| ---------------------------------------- | -------- |
| ユーザーの自由回答で出た内容             | 🧑       |
| アナロジー確認で精緻化された             | 🔄       |
| AIが選択肢を出した後に選ばれた           | 🤖       |
| 🤖だったがCTOで反対立場を検討して維持    | ✅       |
| 🤖だったがDevil's Advocateの反論に耐えた | 😈       |
| 🧑だったがCTOで反対立場を検討して修正    | 🔄       |

**/ spec への引き継ぎ**:

- 🤖（AI提案採用）が多い → /spec で再検証を推奨
- ✅😈（検証済み）が多い → 堅牢な決定として /spec の前提条件に
- 確信度「低」+ 🤖 → /spec で代替案を含めた再設計を推奨

## メカニズム間の相互作用

```
セッション開始
    │
    ├─ [1] 説明責任フレーミング ← 全体の認知姿勢を設定
    │
    ├─ Round 1-2: 質問と回答
    │   ├─ [2] 自由回答ファースト ← 各質問で適用
    │   ├─ [3] Anti-Sycophancy ← 各応答で適用
    │   └─ [6] Decision Provenance ← 各回答を記録
    │
    ├─ [4] Consider-the-Opposite ← Round 2 後の中間検証
    │
    ├─ Round 3: 技術的制約
    │   ├─ [2] 自由回答ファースト
    │   ├─ [3] Anti-Sycophancy
    │   └─ [6] Decision Provenance
    │
    ├─ [5] Devil's Advocate ← Round 4 の最終検証
    │
    ├─ Round 5: 確信度キャリブレーション
    │   └─ [6] Decision Provenance ← 確信度を統合
    │
    └─ 出力生成
        └─ [6] Decision Provenance サマリー
```

## 効果の限界と認識すべきトレードオフ

### 限界

1. **Chen et al. (2025)の知見**: 事前判断の要請（自由回答ファースト）だけではAI推論の開示による過剰信頼を完全には防げない。複数の対策の組み合わせが必要（本プロトコルの設計思想）

2. **Buçinca et al. (2021)のトレードオフ**: 過度の依存を最も減少させたデザインに対して、被験者は最も低い主観的評価を付けた。「考えさせられる」システムは不人気だがパフォーマンスは向上する

3. **追従性バイアスの根深さ**: Anti-Sycophancy はプロンプト指示レベルの対策であり、モデル自体のRLHF由来の追従傾向を完全に除去することはできない

### トレードオフ

| 対策を強めると...           | 失われるもの                   | バランスポイント                           |
| --------------------------- | ------------------------------ | ------------------------------------------ |
| 自由回答ファーストを徹底    | セッション効率（時間がかかる） | 主要判断のみに適用し、瑣末な確認は選択肢OK |
| CTOを多用                   | ユーザーの認知疲労             | 最大2件に絞る                              |
| Devil's Advocateを強くする  | ユーザーの自信・モチベーション | 「これはDAです」と明示し本意見と区別       |
| Decision Provenanceを詳細化 | 出力の可読性                   | サマリーレベルで十分                       |

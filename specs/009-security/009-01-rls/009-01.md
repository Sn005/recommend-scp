# Story: RLS拡充・DB層セキュリティ

## 親EPIC

[009: セキュリティ強化](../009-security.md)

## ユーザーストーリー

**ペルソナ**: システム運用者
**目的**: 全Supabaseテーブルにrow Level Securityポリシーを設定する
**価値**: anonキーでの不正な書き込みをDB層で防止し、データの整合性を担保する
**理由**: 現状`article_translations`のみRLSが設定されており、他テーブルが保護されていない

> システム運用者として、全Supabaseテーブルにrow Level Securityポリシーを設定して、anonキーでの不正書き込みをDB層で防止したい。なぜなら現状ほとんどのテーブルがRLS未設定で保護されていないから。

## Acceptance Criteria

### AC-1: ユーザーデータテーブルのRLS

- [ ] WHILE visitors, view_history, feedback, recommendation_log, favorites テーブルがアクセスされる際
      THE SYSTEM SHALL RLSが有効化されている
      AND SELECT は全ユーザーに許可される
      AND INSERT, UPDATE, DELETE は `auth.role() = 'service_role'` のみ許可される

### AC-2: マスターデータテーブルのRLS

- [ ] WHILE scp_articles, scp_embeddings, tags, tag_dictionary, article_tags, tag_localizations, supported_languages, pipeline_runs, retry_queue テーブルがアクセスされる際
      THE SYSTEM SHALL RLSが有効化されている
      AND SELECT は全ユーザーに許可される
      AND INSERT, UPDATE, DELETE は `auth.role() = 'service_role'` のみ許可される

### AC-3: 既存機能への影響なし

- [ ] WHEN RLSポリシー設定後に全APIエンドポイントを実行した際
      GIVEN service_roleキーでSupabaseに接続している場合
      THEN 既存の全機能が正常に動作する

## 備考

- RLSポリシーは `article_translations` の既存パターンを踏襲する
- APIサーバーは `service_role` キーで接続しているため、RLS設定後も既存機能に影響なし
- anonキーでの直接アクセスのみが制限される

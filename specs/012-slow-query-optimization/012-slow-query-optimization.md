# EPIC: スロークエリ最適化

## ユーザーストーリー

**ペルソナ**: 開発者（プロジェクトオーナー）
**目的**: Supabaseダッシュボードで検出されたスロークエリを分析・改善する
**価値**: ユーザー体験の維持・向上と、データ増加に備えた予防的パフォーマンス改善
**理由**: 現在1万件弱のデータ規模でスロークエリが検出されており、放置するとデータ増加に伴い影響が拡大するため

> 開発者として、Supabaseダッシュボードで検出されたスロークエリを分析・改善して、ユーザー体験の維持・向上とデータ増加に備えた予防的パフォーマンス改善を実現したい。なぜなら現在の規模でスロークエリが検出されており、放置するとデータ増加に伴い影響が拡大するから。

## Acceptance Criteria

- [x] WHEN Supabaseダッシュボードの pg_stat_statements データが共有された際
      GIVEN スロークエリが特定されている場合
      THEN 各クエリに対して分析と改善方針が「Why」付きでドキュメント化されている
      AND 改善マイグレーションがリポジトリにコミットされている

- [x] WHEN スロークエリ改善が適用された後
      GIVEN 改善対象のクエリが存在する場合
      THEN Supabaseダッシュボード上のアラートが解消されている
      AND APIレスポンスが目標値（≤ 200ms）以内に収まっている

- [x] WHILE スロークエリ対応を進めている間
      THE SYSTEM SHALL 既存のAPI入出力互換性を維持する
      AND 既存テストが全て通過する状態を保つ

## 備考

### 対応の性質

本EPICはアドホック対応の性質を持つ。Supabaseダッシュボードのアラートを起点に、都度新しいStory（012-03, 012-04...）を追加して対応サイクルを回す構造とする。

### Clarifyセッションでの決定事項

| 観点         | 決定                                             | 理由                                      |
| ------------ | ------------------------------------------------ | ----------------------------------------- |
| 対応スコープ | ピンポイント（インデックス追加・クエリ書き換え） | データ規模が小さく、予防的対応のROIが低い |
| RPC関数変更  | 関数本体の書き換えも許容（入出力互換性維持）     | 最適な改善を可能にする                    |
| 効果検証     | Supabaseダッシュボードのアラート解消で判断       | シンプルかつ実用的                        |
| ドキュメント | マイグレーション + Why記録                       | 意思決定プロセスの学習蓄積が目的          |

### パフォーマンス目標（既存基準踏襲）

| 指標          | 目標値  |
| ------------- | ------- |
| APIレスポンス | ≤ 200ms |
| ベクトル検索  | ≤ 100ms |

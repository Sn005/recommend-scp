# EPIC: 記事表示速度改善

## ユーザーストーリー

**ペルソナ**: 推薦記事を閲覧するユーザー
**目的**: 記事をストレスなく素早く閲覧する
**価値**: 待ち時間が減り、快適な閲覧体験を得られる
**理由**: 記事表示のたびに外部サイトへのHTTPリクエスト+DOM解析が発生し、2-5秒の待ち時間が生じているから

> ユーザーとして、記事をストレスなく素早く閲覧して、快適な閲覧体験を得たい。なぜなら記事表示のたびに外部サイトへのHTTPリクエスト+DOM解析が発生し、2-5秒の待ち時間が生じているから。

## 背景・ボトルネック分析

### 現状の問題

記事表示フローで以下の2つのエンドポイントが**毎リクエストごとに外部サイト（scp-jp.wikidot.com）にHTTPリクエスト**を送信している:

| エンドポイント              | 処理内容                                              | レイテンシ | 呼び出し頻度             |
| --------------------------- | ----------------------------------------------------- | ---------- | ------------------------ |
| `GET /wiki-proxy/:id`       | 外部HTML取得 + linkedom DOM抽出・再構築 + URL書き換え | 500-2000ms | 記事閲覧ごと             |
| `GET /articles/:id/content` | 外部HTML取得 + linkedom DOM解析（title/excerpt抽出）  | 500-1500ms | カード表示・記事閲覧ごと |

### キャッシュ対象の特性

- SCP Wiki記事は**ほぼ静的コンテンツ**（編集頻度は極めて低い）
- 同一記事を複数ユーザーが閲覧しても毎回外部fetchが発生
- wiki-proxyは `Cache-Control: max-age=300` を返しているが、**サーバーサイドキャッシュなし**

### 期待される改善効果

| 指標                           | 現在   | キャッシュ導入後       | 改善率     |
| ------------------------------ | ------ | ---------------------- | ---------- |
| wiki-proxy P95レイテンシ       | 2000ms | 200ms                  | 10倍高速化 |
| articles/content P95レイテンシ | 1500ms | 50ms                   | 30倍高速化 |
| 外部Wikiリクエスト数           | 毎回   | キャッシュヒット時ゼロ | 大幅削減   |

## 技術選定

**Upstash Redis**（REST API ベース）

- Vercel/Railway等のサーバーレス環境と相性が良い
- Free tier: 10,000 commands/day, 256MB storage
- HTTP REST APIのため接続プール管理不要
- `@upstash/redis` SDKで型安全なアクセス

## Acceptance Criteria

- [ ] 2回目以降の記事表示で外部HTTPリクエストが発生しないこと（キャッシュヒット時）
- [ ] キャッシュ未設定環境（Redis接続情報なし）でも既存動作が維持されること
- [ ] 既存テストがすべて通過すること

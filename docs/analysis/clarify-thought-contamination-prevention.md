# /clarify Skill 思考汚染防止: AI提案による暗黙知の歪み対策

> 学術文献の詳細は [clarify-cognitive-science-references.md](./clarify-cognitive-science-references.md) セクション6を参照。

---

## 問題定義

### 現象

AIツール（特にLLM）を使う際、以下のサイクルが発生する:

```
1. AIが大量の情報・サジェストを提供する
2. 人間がそれを処理・選択する認知コストを避ける
3. 人間が自分で考えたはずのことを、AIの提案にすり替えてしまう
4. 「AIが言っていたから」という形で、人間の主体的思考が省略される
```

### /clarify における深刻さ

/clarify の目的は**人間の暗黙知を引き出す**こと。AIが先に選択肢を提示すると、「人間の暗黙知」ではなく「AIが生成した選択肢に対する人間の反応」を記録してしまう。

これは /clarify の存在意義を根本から損なう:

| 本来の /clarify           | 汚染された /clarify                  |
| ------------------------- | ------------------------------------ |
| 人間の暗黙知 → 形式知     | AI生成の選択肢 → 人間の追認 → 形式知 |
| 人間が「考え出す」        | 人間が「選ぶ」だけ                   |
| 所有感（ownership）が高い | 所有感が低い                         |

## 関連する認知バイアス

### 複合的に作用する5つのバイアス

| バイアス                                              | メカニズム                                   | /clarify での発現                    |
| ----------------------------------------------------- | -------------------------------------------- | ------------------------------------ |
| **自動化バイアス** (Mosier & Skitka, 1996)            | AIの出力をヒューリスティックな代替として使用 | AIの選択肢をそのまま採用             |
| **アンカリング効果** (Tversky & Kahneman, 1974)       | 最初の情報が判断に不釣り合いな影響           | AIが先に出した概念が思考を制約       |
| **認知的オフローディング** (Risko & Gilbert, 2016)    | 思考の外部委託で認知負荷を軽減               | 「AIに聞けばいい」と考えることを放棄 |
| **デフォルトバイアス** (Samuelson & Zeckhauser, 1988) | AIの提案がデフォルトとして機能               | AIの選択肢から外れることに認知コスト |
| **アルゴリズム感謝** (Logg et al., 2019)              | アルゴリズムの判断を人間より信頼             | AIの提案を自分の判断より優先         |

### 問題が深刻化する条件

1. **認知負荷が高い時**: 時間的プレッシャー、マルチタスク → System 1（直感的思考）に依存
2. **AIの出力が流暢な時**: LLMの流暢な文章は「正確さ」と誤認される
3. **反復使用時**: 4ヶ月のLLM使用で認知的関与が漸進的に低下（MIT Media Lab）
4. **不確実性が非表示の時**: LLMが確信度を伝えないと、ユーザーは過大評価する
5. **ワンクリック受け入れUI**: フリクションレスなインターフェースが過度の依存を助長

## 対策: 認知的強制関数（Cognitive Forcing Functions）

Buçinca et al. (2021) が提唱・実験的に検証した最も有効な対策。

### 核心原理

> **AIの提案を見せる前に、まず人間に自分の判断を記録させる**

### 4つの手法

| 手法                   | 説明                                     | /clarify への適用                                      |
| ---------------------- | ---------------------------------------- | ------------------------------------------------------ |
| **事前コミットメント** | AI提案の前に自分の判断を記録             | 自由回答で先に考えを表現させてからアナロジーを提示     |
| **段階的開示**         | AI提案を即座に表示せず、要求するまで隠す | まず人間の回答を受けてから、確認のアナロジーを提示     |
| **チェックリスト**     | AI提案受け入れ前に確認項目を通過         | 「この回答はあなた自身の考えですか？」の所有権チェック |
| **タイムアウト**       | 一定時間の「冷却期間」を強制             | 回答間の熟考タイムを設計に組み込む                     |

### トレードオフ

> 過度の依存を最も減少させたデザインに対して、被験者は**最も低い主観的評価**を付けた。

つまり「考えさせられるシステムは不人気だがパフォーマンスは向上する」。/clarify ではこのトレードオフを理解した上で、ユーザー体験とのバランスを取る必要がある。

## /clarify への具体的設計原則

### 原則1: 自由回答ファースト（Elicitation-First）

```
【推奨する順序】
1. 人間が自分の考えを自由に表現する（事前コミットメント）
2. AIが確認のためにアナロジーを提示する（段階的開示）
3. 人間が自分の考えとAIの提示を比較する
4. 人間が最終判断を下す

【避けるべき順序】
1. AIが選択肢を提示する ← ここでアンカリングが発生
2. 人間が「どれが近いか」を選ぶ
3. 認知的怠惰により、最も楽な選択肢を採用
```

**実装例**:

```
AI: 「このシステムの拡張性について、あなたが最も重要だと思うことは何ですか？」
     （自由回答を促す。選択肢を提示しない）

User: 「後から機能を追加できるようにしたい」

AI: 「なるほど。『後から追加』について少し掘り下げさせてください。
     あなたが今イメージしているのは...
     設定ファイルで切り替えるイメージ？
     それともプラグイン的に後から差し込む拡張性？」
     （回答を受けてからアナロジーを提示）
```

### 原則2: アナロジーは「確認」であって「提案」ではない

二者択一のアナロジーは、ユーザーの回答を**確認・精緻化**するために使う。回答を**生成**するために使ってはならない。

```
【良い使い方: 確認としてのアナロジー】
User: 「シンプルにしたい」
AI: 「あなたが言う『シンプル』は、
     モノリス的な一枚岩の方向？
     それとも疎結合だけどインターフェースがシンプルな方向？」
→ ユーザーが既に持っている暗黙的イメージを明確化

【悪い使い方: 提案としてのアナロジー】
AI: 「拡張性についてはいくつかのアプローチがあります:
     A) プラグインアーキテクチャ
     B) マイクロサービス
     C) Feature Flag
     どれが良いですか？」
→ AIが「答えの空間」を定義してしまい、ユーザーの思考を制約
```

### 原則3: 所有権チェック（Ownership Check）

定期的に「この回答は本当にあなたの考えですか？」という**メタ認知的プロンプト**を挿入する。

```
AI: 「ここまでの整理で、[要約]ということですね。
     これはあなた自身の考えとして合っていますか？
     それとも私の質問の流れに沿って答えただけで、
     本当はもっと違う感覚がありますか？」
```

### 原則4: 差分の明示

AIが確認のアナロジーを提示した後、ユーザーの当初の回答からどう変化したかを明示する。

```
AI: 「最初のあなたの回答: 『シンプルにしたい』
     アナロジー確認後: 『疎結合だけどインターフェースはシンプル』
     この変化は、あなたのイメージが明確になったものですか？
     それとも私のアナロジーに引っ張られた感覚がありますか？」
```

### 原則5: Tool, not Oracle

/clarify は「正解を教えるオラクル」ではなく「思考を支援するツール」として設計する。

| Oracle的な振る舞い（禁止）    | Tool的な振る舞い（推奨）                           |
| ----------------------------- | -------------------------------------------------- |
| 「ベストプラクティスはXです」 | 「あなたの文脈ではどういう基準で判断しますか？」   |
| 「一般的にはAが良いです」     | 「AとBの間で、あなたが重視するのはどちらの側面？」 |
| AI が結論を提示               | 人間が結論に到達するのを支援                       |

## 既存設計との統合

### エンジニアリングアナロジーとの関係

現在の設計（[clarify-engineering-analogy-strategy.md](./clarify-engineering-analogy-strategy.md)）では、二者択一のアナロジーが中心。これ自体は有効だが、**提示順序**が重要:

| 現在の設計                        | 改善後の設計                                            |
| --------------------------------- | ------------------------------------------------------- |
| 抽象的回答 → 即座にアナロジー提示 | 抽象的回答 → 掘り下げ質問（自由回答）→ アナロジーで確認 |

つまり、アナロジー提示の**前に1ステップ挟む**。これにより:

- 人間が先に考える機会を確保（事前コミットメント）
- アナロジーが「提案」ではなく「確認」として機能
- アンカリング効果を最小化

### Phase設計への組み込み

```
Phase 1: 目的・背景の確認
  → 自由回答中心。AIは質問のみ

Phase 2: 定義の明確化
  → 自由回答 → アナロジーで確認（Elicitation-First）

Phase 3: トレードオフの掘り下げ
  → 自由回答 → 二者択一で確認（Elicitation-First）
  → 所有権チェック挿入

Phase 4: 合意形成
  → 差分の明示。変化箇所の所有権確認
```

## 8つの設計原則サマリー

| #   | 原則                                                         | 根拠                                          |
| --- | ------------------------------------------------------------ | --------------------------------------------- |
| 1   | **自由回答ファースト**: AI提案の前に人間の判断を記録         | 認知的強制関数 (Buçinca et al. 2021)          |
| 2   | **アナロジーは確認**: 提案ではなく確認として使用             | アンカリング効果 (Tversky & Kahneman 1974)    |
| 3   | **所有権チェック**: 定期的にメタ認知的プロンプトを挿入       | 自動化バイアス (Mosier & Skitka 1996)         |
| 4   | **差分の明示**: 当初の回答からの変化を可視化                 | デフォルトバイアス                            |
| 5   | **Tool, not Oracle**: 正解を教えず、思考を支援               | Stanford HAI                                  |
| 6   | **意図的な摩擦**: ワンクリック承認を避け、確認ステップを挟む | Design Friction                               |
| 7   | **不確実性の明示**: AIが確信度を伝える                       | 認知的オフローディング (Risko & Gilbert 2016) |
| 8   | **段階的開示**: 情報を一度に出さず、段階的に開示             | 認知負荷理論 (Sweller 1988)                   |

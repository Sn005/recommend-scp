# /clarify Skill 改善分析: エンジニアリングアナロジー戦略

## 背景

/clarify Skillは暗黙知抽出の最上流工程を担うが、実運用で**抽象的な回答が具体化しない**問題がある。

### 現状の課題

```
AI: 「UIの複雑さとデータ精度、どちらを優先しますか？」
User: 「シンプルな方がいい」
AI: （「シンプル」の定義が不明。specに落とせない）
```

「シンプル」「柔軟」「ちゃんと」といった形容詞は、回答者の文脈では具体的な意味を持っているが、AIには解像度が足りない。これが /clarify → /spec の引き継ぎで**情報損失**を生む原因。

---

## 提案: エンジニアリングアナロジーによる具体化

### 核心アイデア

抽象的な回答に対して、**エンジニアリングの一般的概念を比喩として返す**ことで、回答者が「あ、そっちの意味です」と瞬時に具体化できるようにする。

### なぜエンジニアリングか

/clarify のユーザーは全員エンジニア。つまり：

- **発見コスト0**: ユーザーのドメイン知識を探る必要がない
- **精度が高い**: 技術概念は定義が明確で曖昧さが少ない
- **即座に共有地盤**: 「モノリスvsマイクロサービス」と言えば全員が同じ構造を想像する

### アナロジーの引き出し階層

```
優先度1: エンジニアリング一般知識 ← 常に使える安定ベース
優先度2: セッション内で拾った比喩 ← ユーザーが自然に使ったら乗り換え
優先度3: プロジェクト文脈         ← 補助的に使用
```

- 優先度1は**無条件で使用可能**。全セッションで共通。
- 優先度2は「ユーザーが別のドメインの比喩を使った」場合に、そのドメインに合わせてアナロジーを切り替える。例: ユーザーが料理の比喩を使ったら、それ以降は料理で返す。
- 優先度3はプロジェクト固有のコンテキスト（SCP財団、推薦システム等）を利用。

## アナロジーマッピング

### 基本パターン

| 抽象的回答                 | アナロジーで返す                                                               | 引き出される具体             |
| -------------------------- | ------------------------------------------------------------------------------ | ---------------------------- |
| 「シンプルがいい」         | 「モノリスとマイクロサービスで言うと、モノリス寄りの一枚岩でまず作る感覚？」   | アーキテクチャの粒度が明確に |
| 「柔軟に対応したい」       | 「設定ファイルで切り替えたい？それともプラグイン的に後から差し込める拡張性？」 | 拡張の方向性が確定           |
| 「ちゃんと分けたい」       | 「関心の分離で言うと、レイヤー分離？それとも機能単位のコロケーション？」       | 分離の軸が明確に             |
| 「速い方がいい」           | 「レイテンシの話？それともスループットの話？」                                 | パフォーマンス要件が具体化   |
| 「安全にやりたい」         | 「型安全の話？認証認可の話？それともデータの整合性保証？」                     | セキュリティ観点が特定       |
| 「あとで変えられるように」 | 「Feature flagで切り替え？Strategy patternで差し替え？DBの設定値で動的変更？」 | 変更可能性の実装レベルが確定 |

### ドメイン別アナロジー辞書

#### アーキテクチャ系

| 対立概念                      | 使いどころ           |
| ----------------------------- | -------------------- |
| モノリス vs マイクロサービス  | 全体構造の粒度判断   |
| Eager loading vs Lazy loading | 処理タイミングの判断 |
| Push vs Pull                  | データ配信方式の判断 |
| 同期 vs 非同期                | 処理の待ち方の判断   |
| Fat client vs Thin client     | 責務の配置判断       |

#### データ設計系

| 対立概念                         | 使いどころ                 |
| -------------------------------- | -------------------------- |
| 正規化 vs 非正規化               | データ構造の冗長性判断     |
| CQRS (Read/Write分離)            | 読み取りと書き込みの最適化 |
| Event sourcing vs State snapshot | 履歴の持ち方               |
| Hard delete vs Soft delete       | 削除の扱い                 |

#### 運用系

| 対立概念                  | 使いどころ                 |
| ------------------------- | -------------------------- |
| Blue-Green vs Canary      | リリース戦略               |
| Circuit breaker vs Retry  | 障害対応戦略               |
| CAP定理（C/A/Pのうち2つ） | 分散システムのトレードオフ |

## 知識レベルへの対応

ユーザーのエンジニアリング知識には幅がある。アナロジーの難易度を**3段階**で用意し、相手の反応に応じて調整する。

### Tier 1: ユニバーサル（全エンジニア共通）

誰でも知っている概念。安全に使える。

```
- 変数 vs 定数（固定か可変か）
- if/else vs switch（条件分岐の数）
- 配列 vs オブジェクト（順序か名前アクセスか）
- 同期 vs 非同期（待つか待たないか）
- キャッシュ（速度 vs 鮮度のトレードオフ）
- ログレベル（info/warn/error の粒度選択）
```

**使い方の例:**

```
User: 「エラーはちゃんと処理したい」
AI: 「ログレベルで言うと、全部errorレベルで記録したい？
     それとも warn と error を分けて、軽微なものはwarnで流す感覚？」
```

### Tier 2: 中級（実務経験あれば共通）

数年の実務経験があれば通じる概念。

```
- モノリス vs マイクロサービス
- REST vs GraphQL
- SQL vs NoSQL
- Feature flag
- CI/CD パイプライン
- ORM vs 生SQL
```

**使い方の例:**

```
User: 「データの取り方を柔軟にしたい」
AI: 「REST的に固定エンドポイント + クエリパラメータで絞り込む感じ？
     それともGraphQL的にクライアント側が欲しいフィールドを指定する感じ？」
```

### Tier 3: 上級（設計経験者向け）

アーキテクチャ設計の経験がないと通じにくい概念。

```
- CAP定理
- CQRS / Event Sourcing
- Saga パターン
- Hexagonal Architecture
- Back pressure
```

**使い方の例:**

```
User: 「整合性を保ちたい」
AI: 「CAP定理で言うと、ネットワーク分断時に
     一貫性(C)を取って一時的にエラー返す？
     それとも可用性(A)を取って多少古いデータでも返す？」
```

### 適応ルール

```
1. 初回はTier 2から開始（最も広いカバー範囲）
2. ユーザーが「それ何？」と聞いたら → Tier 1に下げる
3. ユーザーが上級概念を自ら使ったら → Tier 3に上げる
4. 判断つかない場合はTier 1にフォールバック
```

## SKILL.md への反映案

### 追加セクション: 「アナロジー活用ルール」

質問生成ルールの中に以下を追加する：

```markdown
### アナロジー活用ルール

抽象的な回答に対して、エンジニアリング概念を比喩として返し、具体化を促す。

**原則:**

1. 常にエンジニアリング概念をベースに比喩を構成する
2. 二者択一の対立概念を提示し、「どちら寄り？」と聞く
3. ユーザーがセッション中に別ドメインの比喩を使ったら、そちらに乗り換える

**難易度調整:**

- 初回: Tier 2（中級）から開始
- 相手の反応で Tier 1〜3 に適応
```

### question-templates.md への反映案

各テンプレートに「アナロジー例」フィールドを追加：

```markdown
### 質問: 「[用語]」の定義

[質問本文]

**アナロジー例（抽象回答時に使用）:**

- 「シンプル」→ 「モノリス的な一枚岩？それとも疎結合だけどインターフェースはシンプル？」
- 「柔軟」→ 「設定ファイル的？プラグイン的？API的？」
```

# UI探索フェーズ運用ガイド

UI探索フェーズの運用方法をまとめたガイドです。

## 1. フェーズの位置づけ

| 項目         | 内容                                          |
| ------------ | --------------------------------------------- |
| 目的         | QA・シナリオテストを妨害するUI地雷を除去      |
| 前提         | 仕様駆動開発（SDD）とは独立したアドホック対応 |
| 終了条件     | 主観的判断（個人開発）                        |
| 対象ブランチ | main（QAブランチは触らない）                  |

### なぜUI探索フェーズが必要か

フロントエンドのUIには、仕様に書ききれない以下の問題が存在します：

- 違和感（色が薄い、余白がずれている）
- 誤操作誘発（削除ボタンが保存に見える）
- 視認性問題（状態が分からない）

これらをシナリオテスト中に発見・修正すると、QA対象が動的に変化し、テストの信頼性が損なわれます。そのため、QAフェーズを"静的"に保つための**事前UI探索フェーズ**を設けています。

## 3. Skill使用方法

### /bug-report（バグ報告）

違和感を発見したら、自然言語で報告します。

**発動方法:**

```
「推薦画面のボタンの色が薄くて見づらい」
「お気に入り画面のアイコンがずれてる」
「/bug-report」
```

**処理内容:**

1. 画面・コンポーネントを特定
2. 比較対象（モック/トークン/AC）と照合
3. バグ認定・ラベル決定
4. GitHub Issue作成

**クラウド環境の場合:**

gh CLIが使えない場合、テンプレートが出力されます。GitHub Web UIでコピペしてIssue作成後、URLを入力してください。

### /bug-fix（バグ修正）

蓄積されたIssueをまとめて修正します。

**発動方法:**

```
「type:ui-bug のIssueを修正して」
「バグを修正して」+ Issue一覧URL
「/bug-fix」
```

**処理内容:**

1. Issue一覧を取得
2. 同一原因でグルーピング
3. 修正計画を提示（承認待ち）
4. バッチ修正実行
5. PR作成（複数Issue紐付け）

## 4. ラベル運用

### 重要度の判断基準

| ラベル     | 基準                  | 例                               |
| ---------- | --------------------- | -------------------------------- |
| `critical` | 誤操作誘発/データ損失 | 削除ボタンが保存ボタンに見える   |
| `major`    | 状態不明/操作支障     | ローディング中か完了か分からない |
| `minor`    | 視認性/美観           | 色が薄い、余白がずれている       |

### 画面ラベル

| ラベル              | 対象                 |
| ------------------- | -------------------- |
| `screen:onboarding` | オンボーディング画面 |
| `screen:recommend`  | 推薦画面             |
| `screen:favorites`  | お気に入り画面       |
| `screen:common`     | 共通コンポーネント   |

### 状態ラベル

| ラベル               | 意味                     |
| -------------------- | ------------------------ |
| `status:open`        | 未対応                   |
| `status:in-progress` | 対応中                   |
| `status:fixed`       | 修正済み（PRマージ待ち） |
| `status:wontfix`     | 意図的に対応しない       |

## 5. 判断記録

### 修正した理由の記録

- PRの修正内容テーブルに記載
- Issue本文の「提案される修正方針」に記載

### 修正しなかった理由の記録（wontfix）

対応しないと判断した場合：

1. Issueに理由をコメント
2. `status:wontfix` ラベルを付与
3. Issueをクローズ

**理由の例:**

- 仕様通りの動作
- 修正コスト > 効果
- QAフェーズで再評価予定

## 6. 比較対象の優先順位

### UI対象の場合

```
1. モックアップHTML（mockups/*.html）
   └─ ビジュアルの差分を確認

2. デザイントークン（mockups/design-tokens.css）
   └─ 色・spacing・font等の値を確認

3. specファイルのAC
   └─ 仕様との差分を確認

4. 人間の違和感記述
   └─ 上記で検出できない場合
```

### 参照ドキュメント

| ドキュメント           | パス                                 |
| ---------------------- | ------------------------------------ |
| デザインガイドライン   | `mockups/DESIGN_GUIDELINES.md`       |
| デザイントークン       | `mockups/design-tokens.css`          |
| 推薦画面モック         | `mockups/header-6-minimal-2btn.html` |
| お気に入りモック       | `mockups/favorites-v2.html`          |
| オンボーディングモック | `mockups/onboarding-v2.html`         |

## 7. QAフェーズとの連携

### フェーズの関係

```
UI探索フェーズ（本ガイド）
    ↓ mainブランチにマージ
QAブランチにリベース
    ↓
シナリオテスト（QAフェーズ）
```

### 注意事項

- UI探索フェーズで `wontfix` としたものはQAフェーズで再評価可能
- UI探索フェーズの修正はmainにマージ後、QAブランチにリベース
- QAブランチへの直接修正は禁止

## 8. よくある質問

### Q: どこまで細かく報告すべき？

A: 「ユーザーが迷うか」を基準に判断してください。

- 迷う可能性がある → 報告する
- 美観のみの問題 → minor として報告（対応は後回し可）

### Q: wontfixの判断基準は？

A: 以下の場合はwontfixを検討：

- 仕様書に明記されている動作
- 修正コストが効果に見合わない
- QAフェーズで改めて判断したい

### Q: クラウド環境でgh CLIが使えない場合は？

A: テンプレートが出力されるので、GitHub Web UIでコピペしてIssue作成してください。作成後にURLを入力すれば、追跡可能になります。
